TL;DR

Start with the problem you are debugging. Each diagnosis links to an LSP pattern that keeps the ERC mental model but adds missing context around metadata, permissions, receiver awareness, and account UX.

Problem cluster

Token transfer problems

Approvals, recipient validation, transfer context, and hooks are where ERC20-era assumptions start to leak into product UX.

ERC20 approval risks Approvals split intent across approve and transferFrom, which creates stale allowance, phishing, and UX review problems. LSP7 uses operators, transfer data, and receiver notifications. Universal Profiles can add LSP6 account permissions around the action. ERC20 transfer hooks (no receiver hook on ERC20) ERC20 transfers do not ask the recipient contract whether it can handle or react to the asset. LSP7 transfers integrate with LSP1 Universal Receiver and include a force parameter plus a data payload. ERC1155 complexity (multi-asset contracts) One ERC1155 contract can mix fungible, semi-fungible, and unique items, so apps pay a decoding and indexing tax. LSP7 covers fungible/semi-fungible, LSP8 covers identifiable assets. The semantic split lives in the standard.

Problem cluster

NFT metadata problems

NFT projects quickly outgrow a single tokenURI when metadata needs to be dynamic, per-token, verifiable, or app-readable.

ERC721 dynamic metadata ERC721 tokenURI is simple and widely supported, but dynamic traits often depend on servers, refresh buttons, and marketplace-specific behavior. LSP8 combines bytes32 token IDs with ERC725Y storage and LSP4 metadata patterns for richer collection and token-level metadata. ERC721 safe transfer problems safeTransferFrom only checks IERC721Receiver, so mixed-asset contracts and downstream calls still strand NFTs and ERC20s. LSP1 Universal Receiver is one hook for all asset types. LSP7 and LSP8 use it through the transfer force flag. ERC721 tokenId uint256 limitation uint256 IDs are efficient, but richer identifiers often need extra mapping layers. LSP8 token IDs are bytes32, which can represent hashes, serials, encoded references, or numeric IDs.

Problem cluster

Wallet and account problems

EOAs are useful primitives, but consumer-grade apps need profile metadata, scoped access, recovery, signatures, and safer delegation.

smart contract wallet permissions A single private key cannot express app-specific authority, device roles, recovery access, or limited contract calls. Universal Profiles use LSP6 Key Manager permissions and allowed calls to scope controller keys. social recovery smart wallets Seed phrases are a single point of failure. Recovery should be a permission graph, not a backup phrase. A Universal Profile can register guardian or threshold controllers through LSP6 without giving up self-custody. EIP-4337 alternatives ERC4337 layers a separate UserOperation pool, bundler, and EntryPoint on top of EOAs. Most teams do not want to run that infrastructure. Universal Profiles use LSP0 + LSP6 + LSP25 + LSP20 to deliver smart-account UX without bundlers.

Problem cluster

Onboarding and receiver problems

The hardest adoption problems are often outside the token interface: gas, notifications, spam assets, and contract reactions.

gasless transactions smart accounts New users often need native tokens before they can do anything, which breaks onboarding. LSP25 relay calls let Universal Profile actions be signed by a controller and submitted by a relayer. contract extension after deployment Adding behavior to a deployed contract usually means proxies, diamonds, or off-chain modules. Each carries upgrade authority or storage risk. LSP17 standardizes a fallback router so contracts can register new function selectors without an upgrade authority. wallet vs universal profile "Smart wallet" can mean an EOA UI, a Safe, a 4337 account, or something else. Apps integrating "all wallets" carry the complexity. A Universal Profile is one account shape: LSP0 contract, LSP3 metadata, LSP6 permissions, LSP1 hooks.
